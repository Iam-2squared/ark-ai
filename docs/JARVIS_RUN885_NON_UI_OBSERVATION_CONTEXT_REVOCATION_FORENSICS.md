## 1. Direct vs fixture observation identity boundary

Before this run, `ObservationEnvelope.__post_init__` admitted exact UTF-8 labels containing NUL although `observation_fixture_adapters._preflight_fixture_metadata` already rejected NUL in native-facing source/privacy labels. The opt-in direct class and disconnected payload adapter could therefore disagree about an ambiguous text identifier. This run added a direct-envelope NUL refusal to source_id, adapter_id and privacy_scope in `src/ark/observations.py` (source commit `e223ac241974b106477afbcf33f7df20d1accff7`), plus seven synthetic parameter cases covering all three direct fields, both caller-settable fixture fields, and two accepted boundary-safe labels (`tests/test_observation_nul_metadata_consistency_run885.py`, commit `0fe3c10106065771c240cb32132bc235a24a5634`). The fixture cases assert that invalid metadata reaches **zero** payload SHA-256 calls; no real source capture or private persistence is involved. Fixture IDs and unrelated frozen contracts are not changed.

## 2. Personal Context reflected metadata ingress

`MemoryRecord.__post_init__` normally creates a `MappingProxyType` of metadata, yet a frozen slotted record can still be reflectively changed via `object.__setattr__`. The optional Personal Context reviewer previously processed `tuple(sorted(record.metadata.items()))` without verifying this exact mapping/budget first. Now the reviewer refuses replaced non-mappingproxy carriers, more than 64 entries, non-exact key/value strings, and keys/values longer than the existing MemoryWrite 4096-character limit **before private row content hashing or metadata sorting** (`src/ark/personal_context_review.py`, commit `c1092cd7e8fde176facf2ad12d14ba44884c901c`). Ten synthetic cases are in `tests/test_personal_context_metadata_ingress_run885.py` (commit `188abe8e233102ce6215c7dea03cbcd0ad05b30a`), including a malicious `items()` carrier and an accepted exact-boundary mapping. This is an opt-in projection-side admission hardening, NOT a frozen Memory v1 schema/write rule change. A context bundle still cannot grant dispatch or action permission.

## 3. Historical revocation cross-process failure — forensics only

Read-only reinspection of [CI #43634279883](https://github.com/Iam-2squared/ark-ai/actions/runs/43634279883), Ubuntu Python 3.12, shows **one failed cross-process test** among **15,657 passed / 1 skipped**. In `tests/test_privacy_revocation_cross_process_run425.py` one contender exited after `unsafe revocation SQLite sidecar`, the other returned `REVOKED`, while a separate diagnostic read showed exactly **one durable veto** with min/max timestamp 2000. This is a response-classification failure, not evidence that revocation data was absent. The log does **not** identify which inode was observed or prove the file was safe during the rejection.

Current `src/ark/personal_context_revocation_review.py` has a **single bounded re-lstat only for st_nlink==0 on a regular existing sidecar**, while rejecting nonregular files, linked aliases, orphan sidecars and unsafe main files. That change was later than the historical failure. No new claim of concurrency correctness follows; the future diagnostic lane should classify the exact sidecar name, before/after stat mode and link-count **without exposing raw owner IDs or contents**, exercise cross-process last-close on both Windows and POSIX, and retain the strict loser error contract. Never replace safety refusal with blanket retry, delete another process's WAL/SHM, retry an ambiguous WRITE or treat one persisted veto as issuer consent.
